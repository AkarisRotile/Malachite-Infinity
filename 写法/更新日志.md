## 2026-09-27（晚）｜ 碧翎念涌改无限持续 · 索敌对齐旧版 · 快捷键与本地化真修复

三件互不相干但都由用户当场实测/截图触发的事。

### 一、碧翎念涌（V 键光翼）改为**开关式无限持续**

**用户原话**：「反正你现在也没给光翼做 CD，还不如直接做成开启之后持续时间无限算了。」

**这个判断是对的，改之前的设计自相矛盾**（原实现：`WingTotalFrames = 330`，即 5.5 秒，CD = 0）：
- CD 为 0 → 断了立刻能再按 → 实际可以无缝续到死，那"5.5 秒"没约束任何东西；
- 它只制造两个纯粹的副作用：① 玩家每 5.5 秒低头按一次 V（机械劳动，不是决策）；② 一旦忘按，
  +30% 念伤 / +2 齐射 / 减速就**无声无息掉光**，玩家只会觉得"伤害飘"。
- 也就是说：**没有 CD 的持续时间就是伪装的 CD，而且是个只惩罚粗心的 CD。**

**新语义**：按 V 开启 → 无限持续（跨地图、跨 Boss 战都不断）→ 再按一次 V 关闭。
关闭（而不是自然到期）才播收尾崩解，于是"消散"从**惩罚**变成了玩家的**主动表达**。
死亡 / 离开世界仍会中断。

| 项 | 改动 |
|---|---|
| `Projectiles\MindWingsAura.cs` | 每帧 `timeLeft = 2` 续命（沿用本工程 `OrbitingCrestProj` 已验证写法），消亡一律显式 `Kill()`；新增 `StartDissipate()` / `IsDissipating`，收尾由 18 帧倒计时驱动 |
| `Core\Vfx\VfxDraw.cs` | `DrawMindWings` 的第二个时间参数由「总帧数」改为「消散剩余帧」；**删除 `WingTotalFrames` 常量**（留着只会诱导后来者又写定时，把伪 CD 加回来） |
| `Players\MalachitePlayer.cs` | V 键改为**按当前状态分支**：已开启（且不在收尾中）→ 关闭；否则扣 30 魔力开启。关闭不收费也不退费（这不是两个技能，是同一次开关的两个方向） |
| `Core\StarWebLayout.cs`、`StarNode.cs`、`CrestNodes.cs` | 节点文案去掉"5.5 秒"，改为"再按一次收起（开启后无限持续）"；`IsMindDomainActive` 补注释说明"存在即生效"的判定边界 |

**改之前专门验过"无限持续在数学上是安全的"**（不是想当然）：
`SnapSpringCurve` 把 `snapP` 钳在 1，故 `timer` 很大时恒返回恰好 `1.0`，不回弹不溢出；
羽片颤动是 `sin(timer * 0.15f)` 的纯正弦，每帧固定前进 0.15 rad，天然循环、无累积漂移。
唯一的理论边界是 float 的 ulp 追上 0.15（需连续常驻约 39 小时），不在现实射程内，故不做 timer 取模。

⚠ **未改的数值（留给平衡阶段）**：一次 30 魔力换**永久** +30% 念伤 / 永久减速 / 永久 +2 齐射，
性价比明显高于其他星宿。真要收口，最自然的做法是**改成每秒消耗少量魔力**（念力维持），
而不是把持续时间倒退回定时 —— 别再用"计时"来假装它是消耗品。

### 二、普攻索敌：**我上一轮的判断是错的，旧版本来就有追踪实现**

**用户指出**：「你说原代码中没有跟踪相关代码，这肯定是错的。」——**用户是对的，我错了。**

我此前只看到旧版 `OrbitingMalachiteProj` 的"track"分支（`velocity *= 1.8f`，那确实不是制导），
就下了"旧版没有追踪"的结论。实际旧版有完整实现 `UpdateTrackingTarget()`
（参考版 `Projectiles\MalachiteProjectiles.cs:178-218`），挂在纹章节点 **`巡猎 / Hunt`（ID=1，Cost 4，
与 `贯穿 ID=2` 互斥）** 下，由 `PostAI` 里的 `hasTrack` 分支调用。

> 名称澄清：用户记忆中的节点名是「寻迹」，但工程里 **`寻迹` 是「阶段 8」的名字**（`MalachiteData.cs`），
> 不是星图节点；追踪节点的真名是 **`巡猎`**。两者的效果描述（"普通攻击的飞刀获得自动追踪能力"）指的是同一件事。

**对比后发现的真实差距 —— 缺的是"索敌质量"，不是"追得凶"**：

| 项 | 旧版 巡猎 | 我改前 | 处理 |
|---|---|---|---|
| 索敌半径 | 1200 | 1100 | 对齐 1200 |
| 记忆保持半径 | **1400（有迟滞）** | 1100（同一个值） | **补 `HomingRetainRange = 1400`** |
| 视线判定 | **`Collision.CanHit` 必须有视线** | 无 | **补上** |
| 重扫节流 | **每 3 帧，且只在没目标时** | 每个 AI 步全扫 240 个 NPC | **补 `HomingRescanInterval`** |
| 转向上限 | `Lerp(v, desired, 0.035)` 保速 | clamp 0.052 × 4 步/tick | 保留我方（更强，是用户上一轮要的） |
| 夹角限制 | 无 | 2.2 rad | 保留我方（更强） |

**为什么"缺视线"是真问题**：没有 `Collision.CanHit` 时会锁定墙后的敌人并一路拐进地形，
玩家读到的不是"追踪强"，而是"这刀老往墙上撞"。**为什么"缺迟滞"是真问题**：
没有 1400 的保持半径时，敌人在 1100 边界晃动 → 反复锁上/丢掉 → 飞刀来回抖，手感像电风扇。
另外旧版"续锁不要求视线、只有重新选目标才要求"—— 这个细节我照抄了，
因为贴地战时地形短暂遮挡就脱锁会频繁丢目标。

### 三、快捷键控制界面"糊成一坨" + 本地化中英混排（用户截图）

**现象**：设置 → 控件 → 模组 里三行文字挤压重叠，第 2/3 行显示的是
`Mods.可成长的孔雀翎.Keybinds.碧翎念涌 (Verdant Plumage) DisplayName` 这种**键原文**。

**根因（两段叠加）**：
1. 三条快捷键里**只有「与孔雀翎对话」有本地化条目**，另两条没有 → tML 查找失败时**不报错**，
   而是把键原文当显示文本回退；
2. 那条回退字符串远宽于控件列表的标签栏 → 换行到第二行，而行高是固定的 → **压在下一行上**。
   （同一渲染路径见 tML `ConfigElement.DrawSelf`：`Height.Set(30f, 0f)` 固定行高 + 带最大宽度的绘制。）

**修复**：
| 项 | 改动 |
|---|---|
| `Localization\zh-Hans_Mods.可成长的孔雀翎.hjson` | **新建**：全部键的中文值（43 个叶子键） |
| `Localization\en-US_Mods.可成长的孔雀翎.hjson` | 全部改为**纯英文**，键集合与中文文件**严格一致** |
| `Localization\Mods.可成长的孔雀翎.hjson` | **保持空 `{}`**（刻意：09-25 实证写中文进基础槽位会让配置/语言切换异常） |
| `Core\MalachiteKeybinds.cs` | 键名改为 ASCII 标识符 `TalkToMalachite`/`VerdantPlumage`/`MeleeAttack`；显示名只存在于 hjson |
| `Configs\MalachiteConfig.cs` | 移除过时 `[Label]`/`[Tooltip]`；`[Header]` 标识符改纯 ASCII `Language`/`Performance`/`UI` |
| `build.txt` | `displayName` 由 `可成长的孔雀翎/Malachite Infinity` 改为 `Malachite Infinity`（去掉混排；中文由 `Mods.可成长的孔雀翎.DisplayName` 提供） |

**关键结论（均核对 tML 源码，不是猜的）**：
- `ConfigElement.OnBind` 只读 **`LabelKeyAttribute`**；`LabelAttribute`/`TooltipAttribute` 已被 tML 标 `[Obsolete]`，
  其值**仅在 `Language.GetOrRegister(key, 默认值)` 里当占位默认值**。hjson 有键时属性被完全忽略 →
  那些 `[Label("极简 (流畅优先) / Low")]` 是**死代码**（删掉零像素变化，且正是它们把混排文本灌进了本地化导出）。
- **快捷键只有 `DisplayName`，没有 Tooltip**（`ModKeybind` 只注册这一个键；`UIKeybindingListItem` 只读它）。
  所以"开/关"这类说明**只能塞进 DisplayName**，且必须短 —— 一长就换行压行。
- 键格式：成员 `Configs.<配置类>.<成员>.Label`；枚举选项 `Configs.<枚举类>.<选项>.Label`；
  分节标题 `Configs.<配置类>.Headers.<[Header] 标识符>`；快捷键 `Keybinds.<名字>.DisplayName`。

**验证方式（离线可查的部分）**：用 tML 自带的 `Hjson.dll` 解析两个文件 —— 均解析通过，
各 **43 个叶子键**、**键集合零差异**；再与 C# 侧实际会查找的键逐条交叉核对（Headers 三个标识符、
三个成员、两个枚举的选项键）全部命中。

⚠ **副作用（需告知）**：快捷键**改名字会重置玩家已设的键位**（tML 用 `模组名/键名` 作持久化依据）。
本次三个键位默认值恰好是 Mouse2 / V / F，与改前默认一致，故除非用户手动改过，否则无感。

⚠ **遗留**：`Mods.可成长的孔雀翎.DisplayName` 虽已补进两个 hjson，但 tML 是否用它覆盖 `build.txt` 的
`displayName` 尚未在游戏内验证；若不生效，模组列表会显示英文 `Malachite Infinity`（单语言，仍无混排）。

### 四、设计要点（D23~D28）

- **一张网，三种星**：翎心（免费根）+ 20 星尘（1 点）+ 10 星宿（2 点）+ 5 星核（5 点）= 36 节点。
  全解锁 **65 点**，而全 Boss 首杀 + 事件里程碑约 **47 点** → **必然取不全，构筑才有意义**。
- **五臂 + 双环**：5 条臂（攻/穿/速/暴/念）由内向外 `D1→D2→S→D3→N`；
  两圈环向连线（内环串星尘、外环串星宿）+ 径向后门 R1↔R2 —— 这是"跨臂混搭"的通路。
- **连通规则**：新节点必须与某个已点亮节点有边。右键退还，但**拒绝产生孤儿星**；一键洗点全额退还。
- **D26 击杀语义变更**：旧 5 个纹章节点并入星网，**击杀只解锁购买资格，仍须花点数**。
- **存档迁移**：旧五轨等级按已花点数**全额退还**（免费洗点）+ 尽量把原构筑意图映射成星网节点；
  旧 `crestNodes` 平移为已点亮（老玩家不白丢 5 个节点 = 10 点）。
- **配色优先级改定（用户拍板）**：R5 只管"颜色集中在调色板"，不管色值取向；
  与 AGY 稿冲突时**以 AGY 为准**，做法是把 AGY 色值收编进 `MalachitePalette`（不是就地硬编码）。

### 七、星网几何与状态的两处硬缺陷修正（离线像素量测驱动）

> 这两条**不是观感判断，是量测出来的硬缺陷** —— 也是离线预览台真正的用处。

**① 布局失衡：顶部溢出画布 19px、底部空 30px**
- 根因：五臂角度 `A(k) = −90° + 72°k`，**没有任何一臂朝正下**，墨迹 y 范围是 `[−1.0, +0.809]·R`，天生偏上。
  原实现让**中心点**落在画布正中 (170,170)、R=170 —— 于是上方到顶、下方空一截。
- 修法：让**墨迹**居中而不是中心点居中。`LocalCenter` → `(170, 185)`（= 170 + 0.0955R），`RenderRadius` → **155**
  （顺带让星核 ≈20px 的视觉外延也留在画布内）。预览台 fx_35 的参考线同步更新。
- 实测：墨迹包围盒 `334×319`，中心 `(209.5,260)` vs 画布中心 `(209.5,259.5)` —— **居中误差 0.5px，四边零溢出**。

**② 未点亮的星核在"发白光"（两个独立成因）**
- 成因 A：原实现给未点亮星核套了 `AccentCyan·0.32` 的环 → 只点亮翎心的新档一开星图就有 5 枚青色光斑，像已激活。改为只有「可购买」才给亮环。
- 成因 B（更隐蔽，且是**全项目级**的）：`PrimitiveVfx.StarSpikes` 每根芒是"从**中心点**发散的三角形扇"，
  所有芒共用同一个中心顶点。星核画两层四芒 = **16 个三角形叠在同一像素**，加色混合下 `GreenDark×16` 直接钳制成纯白
  （实测中心 `(145,255,255)`）。
  → 给 `StarSpikes` 增加可选参数 **`holeRadius`**（根部内孔，默认 0 = 与历史行为完全一致，**现有调用点零影响**），
    未点亮取 `r×0.62 / r×0.42` 把根部散开。
- 实测修后：未点亮星核中心 `(12,18,20)`＝背景；点亮星核中心由死白 `(255,255,255)` 变为暖白 `(191,204,180)`，金色透出。
- 顺带：未点亮的星尘/星宿本体亮度 `GreenDark × 0.78 → 0.95`（离线复查测其对比度偏低）。

### 十、★ 实机反馈修正：指针坐标空间搞错了（"鼠标移到节点上选中的不是这个节点"）

**用户实机反馈**：「按键偏移量非常非常非常非常大，把鼠标移到节点上根本选中的不是这个节点」。

**根因**：我为了"修 UI 缩放错位"，把指针位置写成了 `Main.MouseScreen / Main.UIScale`。**这是错的。**
`Main.MouseScreen`（= `Main.mouseX/mouseY`）与 `UIElement.GetDimensions()` **本来就是同一个坐标空间**，直接相减即可。

**证据（tModLoader 自带代码，不是推理）**：
`patches/tModLoader/Terraria/ModLoader/UI/UIFocusInputTextField.cs`
```csharp
Vector2 MousePosition = new Vector2((float)Main.mouseX, (float)Main.mouseY);
if (!ContainsPoint(MousePosition) && Main.mouseLeft)   // ContainsPoint 判定的就是元素自身尺寸
```
同理 `UIScrollbar` 用 `UserInterface.ActiveInstance.MousePosition` 去比 `GetHandleRectangle()`（元素尺寸）。
**两处都是直接比较，没有任何 UIScale 缩放。**

**为什么表现是"非常大"而不是恒定偏移**：除一个比例等于把鼠标坐标整体缩放，误差 = `|1 − 1/UIScale| × 鼠标坐标`，
**随离屏幕原点距离线性放大** —— 越远的节点偏得越狠，所以是"点哪个都不对"而不是"整体偏一格"。

**修法**：`MouseUi()` 改回 `=> Main.MouseScreen;`（并在注释里写明这个坑的完整推理链与反证，避免以后又"好心"加回去）。

**教训**：这是本会话第二次因为**凭推理改坐标/布局**而翻车（第一次是凭离线图断言"笔画塌成发丝"）。
凡涉及坐标系的地方，**先去 tML/原版源码找一处同类代码当锚点**，不要自己推导缩放链。

## 2026-09-25 ｜ 节点节拍改按「发射弹幕数」计算（并发弹幕节点价值回归）

**用户拍板**：剑阵的触发条件改为**按发射的弹幕数**计算，不再按攻击次数——否则「并发弹幕」这个加点节点形同废点。

### 一、问题确认

剑阵此前是 `SpawnSwordArray` **每次普攻无条件调用一次**，与发射了几发弹幕完全无关。
于是「并发弹幕」轨（1 次普攻发 1+N 道飞刀）对剑阵的产出**零影响**——加点只加飞刀、不加剑阵，该节点的收益面被架空。

### 二、改动

| 项 | 旧 | 新 |
|---|---|---|
| 剑阵节拍 | 每次普攻 1 道 | **每累计 10 发弹幕 1 道**（`ArrayEveryNthShot`） |
| 射线节拍 | 每 3 **次普攻** | **每累计 3 发弹幕**（`BeamEveryNthShot`，语义改写） |
| 累加器 | `leftClickBeamCount`（单一计数） | `shotsForBeam` / `shotsForSwordArray`（**两个独立累加器**） |
| 常量 | `ArrayPerShot = 1` | `ArrayEveryNthShot = 10`（旧常量删除） |

**为何射线一并改**：两者本属同一套节拍逻辑，若只改剑阵会留下"一个按弹幕、一个按次数"的隐性差异，日后必被读错。

**实现要点**：累加器在**消费后取模归零**（`shotsForSwordArray %= ArrayEveryNthShot`），而不是单调递增——后者会无限增长且有溢出风险。两个累加器**不可合并**，因为阈值不同（10 / 3）。
未解锁的节点**不推进自己的累加器**（解锁后从 0 起算，不会解锁瞬间补算历史弹幕）。

### 三、数值影响（**需实测确认手感**，调参入口集中在 `CrestNodes.cs` 常量区）

| 并发弹幕等级 | 1 次普攻弹幕数 | 剑阵频率（旧 → 新） |
|---|---|---|
| 0 级（无加点） | 1 | 每 1 次普攻 → **每 10 次普攻**（**疏了 10 倍**） |
| 满级（+5） | 6 | 每 1 次普攻 → **每 1.67 次普攻**（密了 1.67 倍） |

- **并发加点的价值回归**：0 级 → 满级，剑阵产出速率相差 **6 倍**（此前恒为 1 倍）。
- **无加点时剑阵明显变稀**——这是"按弹幕数"的必然结果，若实测觉得基础手感空，把 `ArrayEveryNthShot` 调小即可（一处常量）。

### 四、修改文件（3）

| 文件 | 改动 |
|---|---|
| `Core\CrestNodes.cs` | `ArrayPerShot` → `ArrayEveryNthShot = 10`；`BeamEveryNthShot` 语义注释改写为"发弹幕数"；`SpawnSwordArray` 去掉内部 1 次循环（节拍交由调用方） |
| `Players\MalachitePlayer.cs` | 字段 `leftClickBeamCount` → `shotsForBeam` + `shotsForSwordArray` |
| `Items\PeacockWillowBlade.cs` | `Shoot` 记录**实际发射的弹幕数**（`fired`，注意受 `Math.Min(8, shots)` 封顶影响），两个节点各自累加、取模消费 |

### 五、验证与兼容性

- `Mod-Gate.ps1`：**PASS / FAIL=0**，`error CS = 0`（中途曾漏改 `SpawnSwordArray` 内的旧常量引用，报 1 处 CS0103，已修）。

> **状态：代码已落地并编译通过，但视觉未经验收。** 本条记录的是"根因诊断 + 结构性改造 + 参数单一出处"，

### 一、诊断：刀光为什么几乎看不见（四条根因，均可量化）

起点是检视预览台既有产物 `fx_20_crystal_vs_fluid.png` / `fx_18_crystal_slash.png`（那是更早一轮"晶体感"探索留下的，
**探索未完成、也从未进 mod**）。图里真正被看见的只有那根修长晶刃，扇形条带要很仔细才看得到一点弧。逐层核查后确认四条原因：

| # | 根因 | 证据 |
|---|---|---|
| 1 | **混合模式用 `BlendState.Additive`** | `DrawFanStrip` 原第 1414 行。加色混合无法表达"变暗"，而条带色阶大量落在深翠绿侧（内缘 `tint×0.6`、阴面 `GreenDeep`）→ 这些像素加色贡献≈0。**且**程序化烘焙的拉丝贴图上下边缘羽化到 `alpha=0`（`BakeTrailTexture` 的 `Pow(sin(v·π),1.8)`），加色下羽化区被整体吃掉 |
| 2 | **梭形厚度太薄** | `bladeWidth = rOuter × (0.35×sin(u^0.7·π) + 0.05)`；`rOuter≈200~256` → 最厚仅 20~36px，而挥扫弧长 800~1200px，**厚/长 ≈ 1/40**，视觉上退化成一根线 |
| 3 | **`u` 用顶点序号而非弧长** | `u = i/(subdivisions-1)`。扫得快的帧纹理被拉长、慢的帧被压挤 → 逐帧拉丝密度跳变。鬼切的 `uLenScale = 弧长/瓦片长` 正是为解此 |
| 4 | **白热过渡是断崖** | `colOut = Lerp(tint, White, clamp(u×1.5))`：暗翠 → 纯白之间没有缓冲带，只有"暗"与"死白"两极（预览图右下那个生硬白色色块即此） |

### 二、新建 `Core\Vfx\SlashTuning.cs`：刀光参数**唯一出处**

零 Terraria 依赖。`MalachiteMelee` 原常量**保留**（避免同名歧义与大面积改动），但数值与语义已在本文件成表。

### 三、横截面：双轨 → 多段（四段晶体）

`SlashVfx.BuildFanStrip` 重写，关键变更：

- **任意段数横截面**：顶点布局改为「每列 = 色标数 × 2」，相邻两列对应点连成四边形。新增 `BandProfile` 三档（`Legacy`/`Crystal`/`CrystalSoft`），色标表由 `SlashTuning.StopsFor` 给出。默认 `Crystal` = 内缘软融 30% / 主体 / 白热核心贴外缘(0.90) / 外缘硬切(0.965)。
- **`u` 轴按累积弧长归一化**：预计算 `arc[i] = Σ|Δθ|×r` 再归一，对齐鬼切 `uLenScale`。用 `AngleDelta` 处理 ±π 环绕，避免跨环算出 2π 假弧长。
- **厚度**：`0.35 → 0.62`（新增 `BandMaxThicknessK`，这是可见度第一旋钮），并加 `BandMinThicknessPx = 16` 下限与"不许厚到吃进圆心"的夹取。
- **中立顶点类型 `SlashVertex`**：原先 `BuildFanStrip` 直接写 MonoGame 的 `VertexPositionColorTexture`，而预览台用的是 **FNA** 的同名类型——**两个同名结构体不是同一个类型**。这是"游戏与预览共用同一份构建逻辑"的硬障碍，也是预览台此前只能自己另写一份 `BuildFanStrip` 的原因。改为中立结构后，两端各自转换。

### 四、混合模式改造（游戏端）

`DrawFanStrip`：`BlendState.Additive` → **`BlendState.NonPremultiplied`**。
顶点色按「RGB 与 A 独立」语义提交，结构（alpha）与体色（color）分离 —— 与 `SlashVfx` 的顶点色写法一致，
也让"外缘暗边 / 内缘软融 / 冷却下沉"这三类**压暗**效果第一次成为可能。
同时与 v5.5 确立的"特效直接画进引擎批次"精神一致（本次未新增任何 `End/Begin` 换批次，原有换批次是顶点网格引入时就存在的存量结构）。

绘制调用同步修正：三角数 = `(列数−1) × (色标数−1) × 2`（原先写死 `vertexCount−2`，在四段布局下是错的）；
顶点缓冲 `82 → SlashTuning.FanVertexCapacity`（`40×12 = 480`）。

### 六、**诊断的修正：为什么当初判断"坍缩"是错的**

本节最初记录为"条带因采样点不足而坍缩成一根线"。**该结论已作废**，原因是我当时依赖的预览图本身是失真的：
预览台 `fx_6` 的历史推进是**每帧 1 次**，而游戏内 `RecordPose` 是**每帧 3 次**（sweep 期 3×/帧）。
采样密度差 3 倍，让条带在预览里显得比实机更细——我据此推了一个并不成立的"几何坍缩"结论。

**修正后的事实**（见第七节详述）：条带的**几何是正常的**——诊断输出 `p0=(364,87)`、`pm=(323,222)` 位置正常变化，宽度正常；
顶点色也**完全不暗**（`maxA=242`、`maxLum=232`、`avgA=93`）。
真正的问题是**条带一个像素都没画到画面上**（对照探针证明视口/渲染目标/批次都正常，故障在 `BasicEffect` + `DrawUserPrimitives` 这条绘制路径）。

教训：**先确认预览台本身是否忠实，再根据预览下结论。** 这次我把"工具失真"当成了"被测对象的缺陷"。
**这条判据同时适用于游戏内**——游戏内 `_th` 同样只保留 12 帧（`SlashTrailMax`），所以游戏里条带也是同样的坍缩。

对照台 `fx_26` 已能产出正确的顶点数据：**`vc=480`、`maxA=242`、`maxLum=232`、`avgA=93`** —— 数值上完全不暗、不透明。

### 一、从"无条件普攻派生"变为"节点产物"

上一轮迁入的剑阵是**无条件**的（`ArrayCountOf(stage) > 0` 即生效，stage 3 就开始，每 3 次普攻一批）——与用户"后期节点"的定位冲突，故本次改造为节点门控。

| 项 | 旧 | 新 |
|---|---|---|
| 解锁 | stage ≥ 3 自动 | **击败世纪之花**（`NPC.downedPlantBoss`） |
| 触发 | 每 3 次普攻（stage≥13 每 2 次）预备一批 | **每次普攻生成一道**（`ArrayPerShot = 1`） |
| 一次生成量 | `ArrayCount[]` 表 0→10 把 | 1 道（可调常量） |
| 落点 | `player.Center` | **玩家四周随机方位**，模长 ∈ [110, 300] px |
| 生成方式 | `pendingSwords` 队列，每帧最多出 2 把 | **当帧直接生成**，无队列 |
| 伤害倍率 | `0.15 + (0.5/0.6/0.8/1.0)`，stage≥11 再 ×1.15 | `0.30 ×` 本次普攻（触发频率提高，故下调） |
| 库存上限 | 场上 16 / stage≥13 为 24 | 场上 **12**（`ArrayMaxAlive`，软门控直接拒绝生成） |

**移除的死机制**：`MalachitePlayer.pendingSwords` / `pendingSwordDamage` / `pendingSwordKnockback` 三字段、`PreUpdate` 中的分发块、`leftClickShootCount`、`WillowGrowth.ArrayCount[]` 表与 `ArrayCountOf()`。旧版那套"蓄积 → 每帧限量分发"的间接层在"每次普攻必出一阵"的规则下已无存在意义，留着只会让伤害口径有两个出处。

### 二、三项新能力（本文件此前完全缺失）

**① 随机方位生成**
由 `CrestNodes.SpawnSwordArray` 统一解算：`angle = NextFloat(TwoPi)`、`dist = NextFloat(110, 300)`，落点 = `player.Center + 极坐标偏移`。生成方只负责摆位置，**起始速度由弹幕自己朝玩家解算**——避免"生成点随机 + 速度也随机"导致的两处随机源打架。

**② 穿墙**
`OrbitingWillowProj.tileCollide = false`（全程）。**关键补充**：剑阵射出的飞刀也设为 `tileCollide = false`——否则剑阵本身能穿墙、但它打的飞刀撞墙就没了，"穿墙"形同虚设。这是本次最容易漏的一环，已用生成后立即改写 `Main.projectile[knife].tileCollide` 落实。

**③ 消亡代码**
原版只有"射出飞刀后 `Kill()`"，没有任何消亡表现。本次新增**渐隐消散期**（`WitherFrames = 36`）：
- `BeginWither()`（幂等）：锁渐隐倒计时、`friendly = false`（避免"消散中的剑阵还在打人"）、速度清零。
- `UpdateWither()`：`alpha` 由 100 → 255 爬升（与出场 255 → 100 的渐显**对称**）、旋转减速至 0.35×、光照随进度衰减、晶尘**由外向内收拢**（`NextVector2CircularEdge` 半径随 `1-t` 收缩）、归零时播 `Item27` 并 `Kill()`。
- 触发条件三条：**离玩家超过 `ArraySpawnMaxDist × 1.6`**（被甩开）、**剩余存活不足 `WitherFrames`**（超时兜底）、**蓄力完成射出飞刀**。
- **消亡期不占生成名额**：`CrestNodes.SpawnSwordArray` 统计在场数量时通过 `OrbitingWillowProj.IsWithering` 排除渐隐中的剑阵——否则渐隐的 36 帧会白占 `ArrayMaxAlive` 名额，让上限在高攻速下提前失效。

### 三、追身逻辑（为配合远距离随机落点）

旧版从玩家中心 `×32` 随机方向外抛后在原地减速悬停；新版的落点在 110~300 px 外，若沿用旧逻辑，剑阵会**停在远处不回来**，与"绕在身边"的观感不符。故改为：
- 距离 > `HoverDistance`(190) → 朝玩家解算方向，`Lerp` 向 `MoveSpeedMax`(26) 收敛；
- 距离 ≤ 190 → `×0.86` 迅速悬停。

出场初速按距离加权（`min(26, 10 + dist×0.06)`），远距离生成时更快，避免慢吞吞飘过来。

## 2026-09-01 ｜ 首测反馈修复（特效过曝/巨型光带）

### 根因分析
1. **超巨型光带**：特效绘制误用 `TextureAssets.MagicPixel`（tModLoader 内部纹理，尺寸不可控），按 1x1 写的缩放被放大 → 巨型光带；叠加 additive 加色混合 → 过曝乱闪。

### 修复
| 文件 | 改动 |
|---|---|
| `Core\AdditiveLayer.cs` | 新增 `Pixel` 共享纹理（自建 `Textures/Pixel.png` 1x1，尺寸绝对可控），替代 MagicPixel |
| `Projectiles\MalachiteProj.cs` | 光带 34x3 → **14x1.8**；双层亮点 3.2/5.5 → **2.2/3.4**；alpha 下调（0.85→0.65） |
